## 1. 結論(先に要点)

科学OSの3要素(正規ID・内部Index・マッピング仕様)は、IHL の既存設計と**衝突せず、欠けていた「世界との接続層」を埋める**:

| 科学OS の要素 | IHL の既存資産 | 統合方針 |
|---|---|---|
| Wikidata Q番号(正規ID) | `domain_catalog`(観測対象分類辞書、ADR-H-16) | 辞書エントリに `canonical_id: Q番号` を追加。階層は Wikidata を参照し内部に持たない |
| 内部Index(使用時発行) | 既存の individual_id / capture_id 発行 | 新規エンティティ参照時のみ `canonical_map` イベントを append(使われた瞬間に発行 = 無駄ゼロ) |
| マッピング仕様(専門API対応表) | なし(新規) | `truth/canonical/mapping_event` に Q番号→GBIF/NCBI 等の対応を append-only 保存 |
| 存在確認だけのAPI利用 | R2 no-overwrite・CI安全思想 | 外部APIは読み取り専用・存在確認中心。結果は「使われた対象だけ」キャッシュ(数MB級) |
| 目的→観点→手段→結果テンプレート | **論文6節スキーマ PaperSectionsV1 とほぼ同型**(目的/仮説/条件/検証/フェーズ/ギャップ) | 新スキーマを作らず PaperSectionsV1 に観点ベクトル(観点辞書キー+値+単位+欠損フラグ)を拡張 |
| AI査読パイプライン(7段階) | 知の広場 DET-KN-5(LLM はギャップ節ヒントまで) | **段階1〜5(構造・欠損・再現性・整合性・統計)は決定論コードで実装可能** — LLM 必須なのは段階6(要約・改善提案)のみ。Second Brain 原則3 と完全に一致 |
| フォーク/PR/Issue | github_component_board(GitHub 正本パターン)、fork_history、market/board のイベント基盤 | 観測レコードのフォークは GitHub 正本パターンの水平展開。承認は信頼度スコア(将来) |
| 条件リクエスト | board(掲示板)+ research match | AI査読の欠損検出 → 条件リクエストを board の新カテゴリとして発行 |
| アーキネーター式絞り込みUI | apps/search の5ペイン + domain_catalog | Wikidata 階層をたどる絞り込み。存在確認バッジ。**UI は知の広場ゲート解除後** |

## 2. 追加アーキテクチャ(最小差分)

```
[外部(保存しない)] Wikidata / GBIF / NCBI … ← 存在確認・階層参照のみ
        │ 使われた瞬間だけ
        ▼
[canonical 層(新設・極小)] truth/canonical/
   ├── mapping_event    Q番号 ⇔ 内部Index ⇔ 専門API ID(append-only)
   └── cache/           使われた対象の階層・ラベルのみ(数MB、再取得可能な派生物)
        ▼
[既存 Truth 層] observation / board / research(変更なし — canonical_id フィールドを追記可能に)
        ▼
[知識層] docs/knowledge(K1〜K3)— 観点辞書・査読基準・テンプレートの知識ページ化
        ▼
[AI査読] tools/review_pipeline.py(決定論 5段階)+ Sonnet(段階6の要約・提案のみ)
```

## 3. 画像→ノード→近さ検索(撮影チャンバー構想との接続)

ユーザーのアイデア「ヘラクレスを画像解析し node 化して近さで検索、理想を数値化」は**既に半分実装されている**: `embedding.py`(dinov2 384次元)+ `faiss_index.py` + `scoring.py`(ADR-H-12 加重リランク)。不足は:
1. 標準撮影チャンバー(ColorChecker/ArUco/グリッド)による撮影標準化 → 埋め込みの比較可能性が飛躍的に向上(既にプロジェクト化済み: D:\notes\projects\2026-07-shooting-chamber.md)
2. 「理想像」クエリ(ユーザーが理想の個体像を指定 → 近傍検索)= 既存 search_similar の入力を「登録画像」から「理想参照画像/観点ベクトル」に広げるだけ
3. K3 のテキスト埋め込みと合わせると「言葉でも画像でも近さで探せる」二モーダル検索になる

## 4. フォルダ構成・設計書整理(Phase 6 Stage R で調査→提案)

ユーザー要望「既存の設計書全て調査して整えてほしい」への方針: **いきなり動かさない**。Stage R で全設計書(docs/ 配下+日本語ドキュメント群)の一覧・重複・矛盾・参照切れを調査し、移行マップ(現在地→新配置、リンク書き換え一覧)を提案書として出す。適用は人間承認後(リンク切れが怖いのは要件定義〜設計のトレーサビリティのため)。要件定義書と実装のギャップ一覧(RTM 形式)も同時に作る — 「したいことは要件定義書にほぼ書いてある」ため、これが次の実装バックログの正本になる。
