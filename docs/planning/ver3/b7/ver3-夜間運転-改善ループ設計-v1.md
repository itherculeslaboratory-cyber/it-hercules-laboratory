## 1. 夜間運転アーキテクチャ（V3-AIP-96・Tier S）

### 1.1 一晩の流れ【提案】

```
就寝前（人間・任意）                夜間（AI・無人だが無裁量）              朝（人間・OK/NG のみ）
─────────────────              ──────────────────────────              ─────────────────
ops\schedules\night.json を     スケジューラ起動（§2）                   朝レビュースタック（§4）
確認/編集（どのタスクを           → ランナーがタスク定義を validate         → カード単位に OK / NG
走らせるか。既定は前夜と同じ）      （必須キャップ欠落 = 実行拒否）           → OK: Promote 候補化
                                → ラウンド実行（1ラウンド=1 JSON 追記）    → NG: 理由1行（任意）
                                → 上限到達/成果ゼロ → STOP マーカー        → 迷う1割 = 人間が判断
                                → 成果物をレビュースタックへ積む            （V3-AIP-78）
```

- **夜間に実行してよい仕事の種類**（V3-AIP-96 原文の4種 — `ver3-最終要件定義書-v1.md:832`）: ①台本ドラフト生成 ②wiki ingest・蒸留 ③資料メタ化 ④KPI 集計・改善提案。**この4種以外は夜間タスク化しない**（種類の追加は `00-hq\decisions\` への裁定 append を要する）。
- **夜間 AI に裁量を与えない**: 夜のエージェントは「タスク定義に書かれた success_criteria に向けて回る」だけ。新しい目標の発明・タスク定義の書き換え・スケジュール変更・repo 外への書込は禁止。迷ったら中断して朝スタックに「要判断」カードを積む（ワンクリック全自動禁止 = V3-AIP-78/31）。
- **出力は全てドラフト**: 夜間成果物に直接公開経路はない。公開・投稿ボタンは初期人間ゲート（V3-VID-01 R1、`ver3-最終要件定義書-v1.md:718`）。
- **置き場**（ワークスペース設計 §4.2 準拠）: タスク定義 = `00-hq\night-tasks\<task-id>.md`、スケジュール = `ops\schedules\night.json`、実行ログ = `ops\runs\<YYYY-MM-DD>-<task-id>\round-NN.json`（append-only）、成果物 = 各 system repo 内の draft 置き場（§7.1 で具体化）。

### 1.2 コンポーネント分解【提案】

| # | コンポーネント | 責務 | 実装形（Phase C） |
|---|---|---|---|
| N1 | スケジューラ | 決められた時刻にランナーを起動するだけ。判断ゼロ | §2 選定 |
| N2 | ランナー（night-runner） | タスク定義 validate → キャップ監視 → ラウンド起動（`claude -p` ヘッドレス）→ ラウンドログ追記 → STOP 判定 → レビュースタック積み | 決定論スクリプト 1 本（LLM を使わない。条項①） |
| N3 | 夜間エージェント | 1 ラウンド = 1 回のヘッドレス Claude 実行。タスク定義の goal/success_criteria のみを input とする | `claude -p`（モデルは §3.4 ルーティング） |
| N4 | 朝レビュースタック | 成果物カードの一覧 + OK/NG 記録 | §4（段階案） |
| N5 | KPI 投影 | ラウンド JSON ログ → KPI 表の生成（決定論・再生成可能） | §5 |

- **ランナーは決定論**にする理由: コスト監視・停止判定という「金と安全」の経路に LLM を挟まない（批評家ゲート思想と同じ — 判定は決定論が正、B4 §6.3 査読 6 段と同型）。
- **孫エージェント禁止**: N3 の夜間エージェントはサブエージェントを 1 階層まで（V3-CST-03「探索的委譲は 1 階層に留め孫エージェントを生まない」`ver3-最終要件定義書-v1.md:834`）。試験導入（§7）では**サブエージェント自体を禁止**（1 セッション単独実行）に絞る。

## 2. スケジューラ選定（根拠付き）

### 2.1 比較表【提案】

| 観点 | (a) Claude Code routines/schedule（クラウド） | (b) ローカルスケジューラ（Windows タスクスケジューラ + `claude -p`） | (c) Cloudflare Workers cron |
|---|---|---|---|
| 夜間タスク 4 種を実行できるか | ○（クラウドサンドボックスで agent 実行） | ○（ローカル repo に直接アクセス） | ✗（Workers 上で Claude Code agent は動かない。HTTP 処理のみ） |
| 対象データへの到達 | △ GitHub 経由。**ローカル正本（D:\claude HQ・ops\runs・未 push の draft）に届かない** | ◎ `D:\claude` 階層・repo・ログ全てローカル | ✗ R2/API のみ |
| コスト計測・キャップ強制 | △ 実行単位の細かいトークン計測とラウンド途中停止をこちらの制御下に置きにくい | ◎ ランナー（N2）が各ラウンドの usage を読み、キャップ超過で起動そのものを止められる | — |
| R-6（同意ベース cron）適合 | ○ ユーザーが明示作成 | ◎ ユーザーが 1 コマンドで作成/削除。`schtasks /query` でいつでも全件目視可能。既定 off | ○ |
| V3-SEC-52（夜間の無断外部取得禁止）適合 | △ クラウド実行は WebSearch 等へ逃げやすく、遮断の保証がこちらのコードにない | ◎ ランナーが `--allowedTools` 相当で WebFetch/WebSearch を**不許可に固定**できる | — |
| 実行ログの append-only 保存（ops\runs） | △ ログ正本がクラウド側 | ◎ ラウンド JSON をその場で追記 | △ |
| 追加コスト | サブスク枠内だが計測粒度が粗い | 電気代のみ（PC 稼働が前提） | 無料枠内 |
| 単一障害点 | Anthropic 側の稼働 | **PC がスリープ/電源断だと走らない** | — |

### 2.2 推奨【提案】

**推奨 = (b) ローカルスケジューラ + 決定論ランナー**。決め手は 3 点:

1. **コスト統治の主導権**: 『一日で20ドル』の再発防止（§3）は「ラウンド起動前にランナーがキャップを検査し、超過なら起動しない」という**こちら側コードの決定論チェック**でしか保証できない。クラウド routines はこの検査を挟む場所がない。
2. **V3-SEC-52 の構造的担保**: 夜間エージェントのツール許可をランナーが固定する（外部取得系ツール不許可）。対象は **repo 内データと明示許可済みソースに限定**。「夜は repo の外を見ない」を設定ではなく起動パラメータで強制できる。
3. **ログ正本の所在**: 実行ログは `ops\runs\` に append-only（ワークスペース設計 §4.2）。ローカル実行ならログとランナーが同一境界にあり、朝レビュー・KPI 投影（§5）が repo 内で閉じる。

**併記（棄却ではなく役割分担）**: (a) クラウド routines は「PC が落ちていても走ってほしい軽量スキャン（例: GitHub Issues 要約 = V3-AIP-67）」の**将来候補**として残す（採用時は本書の改訂 + ユーザー裁定）。(c) Workers cron は夜間運転の実行系としては不採用だが、**GMO 明細ポーリング等のサーバ側 system cron**（B4 §5・§6.4）は別系統として Workers cron が正 — 本書のスコープ外。

- PC スリープ問題は試験導入では「その夜だけスリープ無効 or 電源接続」で運用対応し、恒常運転時に wake timer 設定を検討（Phase C 判断）。

## 3. コスト統治（必須設計）

### 3.1 夜間タスク定義スキーマ — 具体値【提案】

機械可読正本は B4 §10 `schemas/night-task.schema.json`（必須キー: `task_id / goal / success_criteria / cost_cap_tokens / cost_cap_usd / time_cap_minutes / max_rounds / zero_result_stop`）。ワークスペース設計 §4.2 の「上限 3 値（max_cost_usd / max_rounds / max_minutes）必須・欠落時実行拒否」は B4 スキーマで `cost_cap_usd / max_rounds / time_cap_minutes` に改名・拡張済み — **B4 の键名を正とする**。本書はその**既定値と上限の上限**を定める:

| キー | 既定値（1タスク） | 上限の上限（これ以上はスキーマ改訂 + 人間裁定） | 根拠 |
|---|---|---|---|
| `cost_cap_tokens` | 500,000 | 2,000,000 | Phase B 実績（1 セッション +1000k〜1500k token 予算 — `PLAN-ver3-phase-b.md:58`）の 1/2〜1/3。夜間 1 タスクは 1 セッションより小さくあるべき |
| `cost_cap_usd` | **2.00 USD** | 5.00 USD | 『一日で20ドル』の 1/10（§3.3） |
| `time_cap_minutes` | 45 | 120 | 朝までに複数タスクを直列消化する余裕（§3.2 総枠と連動） |
| `max_rounds` | 3 | 10 | B4 §10 推奨値 10 は上限側。既定は小さく始める（条項①） |
| `zero_result_stop` | `true`（const。false 不可） | — | B4 スキーマで型レベル強制済み |

### 3.2 1 夜あたり総枠（`ops\schedules\night.json`）【提案】

タスク別上限とは**別に**夜間全体の総枠を持つ（ワークスペース設計 §4.2「夜間全体のコスト上限」）:

```json
{
  "night_window": { "start": "01:30", "end": "06:00" },
  "night_budget_usd": 5.00,
  "night_budget_tokens": 1500000,
  "max_tasks_per_night": 2,
  "enabled": false,
  "enabled_by": null,
  "enabled_at": null,
  "tasks": ["<task-id> の配列。00-hq/night-tasks/ に定義が実在しないものは実行拒否"]
}
```

- `enabled: false` が**既定**（R-6: 同意ベース）。有効化は `enabled_by`（ユーザー名）+ `enabled_at` の記入を必須とし、ランナーは null のとき即終了する。
- **knowledge 書込タスクの直列化検査**（B6 §2.3 からの引き継ぎ検査）: `tasks` 配列に knowledge 層（`docs/knowledge/` 等）へ書き込むタスク定義が同一夜に 2 件以上載っていたら **night.json の validate 不合格 = 当夜起動しない**（§6 S6）。実行時も §3.3 の「1 タスク = 1 セッション直列」により同時書込は構造的に発生しない — B6 の `.ingest-state.lock` は最終防衛線。
- 総枠 5 USD/夜・タスク 2 本/夜。月間の観念上の最大 = 150 USD だが、試験導入（§7）は **1 夜限り**であり、恒常運転の月間予算は運転開始裁定時に別途ユーザーが決める（本書は既定を決めない — 継続的トークン消費の開始は人間ゲート）。

### 3.3 『一日で20ドル』再発防止 — 多層防御【提案】

| 層 | 防御 | 効き方 |
|---|---|---|
| L1 スキーマ | キャップ必須キー。欠落タスクは **validate 不合格 = 実行拒否**（B4 §10 negative TC #27） | 「上限を書き忘れたタスク」が存在できない |
| L2 ランナー | ラウンド開始**前**に累積 usage を検査。`min(タスク残枠, 夜間総枠残)` を超えるなら起動しない。**併せてラウンド自体を有界化**: N3 を `claude -p --max-turns <N>` で起動し、ランナーは `time_cap_minutes` の残分をラウンドのタイムアウトとしてプロセスを強制終了する | 超過は「次のラウンドが始まらない」形で止まる。**検査はラウンド境界のみのため、実行中の 1 ラウンド分だけキャップを超過し得る**（この超過余地自体は --max-turns とタイムアウト kill で有界） |
| L3 STOP マーカー | 上限到達・成果ゼロ・連続失敗で `ops\runs\<run>\STOP`（空ファイル + 理由 1 行）。**STOP 存在下の新ラウンド起動は禁止**（B4 negative TC #28） | ランナー自身がバグっても、再起動後のランナーが STOP を見て止まる |
| L4 総枠 | 夜間総枠到達で**全タスク停止**（当夜はもう何も走らない） | タスク単位の穴あきを夜単位で塞ぐ |
| L5 人間 | 朝レビューに当夜の消費実績カード（tokens/usd/停止理由）を**必ず 1 枚**積む。80% 到達夜は「要注意」フラグ | 監視トリガ = 開発計画 R-01（上限の 80% 到達） |

- multi-agent はトークン約 15 倍（`b2/research-external-knowledge-v1.md` 根拠7 — 開発計画 R-01 より孫引き）。よって夜間は**多エージェント構成を採らない**。1 タスク = 1 セッション直列。

### 3.4 3 層モデルルーティング（V3-CST-03）【提案】

| 層 | 用途 | モデル帯 | 夜間での使用 |
|---|---|---|---|
| 最下層（探索） | wiki ingest スキャン・ファイル列挙・鮮度判定・KPI 集計の下ごしらえ | Haiku 等最下層 | ◎ 夜間の既定層 |
| 中層（生成） | 台本ドラフト・蒸留文・メタ記述の 1 次生成 | Sonnet 等中層 | ○ ランナー起動パラメータ `model` でラウンド別に明示指定した場合のみ（モデル指定は**タスク定義のキーではない** — B4 §10 スキーマは `additionalProperties: false` でモデルキーを持たない。§7.1 参照） |
| 最上層（統合・裁定） | 設計判断・レビュー | Opus/Fable 級 | **✗ 夜間では使わない**。統合が要る成果は朝スタックに「要判断」で積む |

- 委譲テンプレ（タスク定義 md）には**トークン予算・再試行上限・エスカレーション条件を必須明記**（V3-CST-03）。B4 スキーマの `escalation` キーがこれに当たる。
- 探索的委譲は 1 階層まで・孫エージェント禁止（同上）。決定論で済む処理（ファイル走査・日付比較・集計）はモデルを呼ばずランナー/スクリプトで行う（条項①: 決定論優先・モデル最小化）。

## 5. 改善ループ / KPI 設計

### 5.1 改善ループ — Phase A/B 実証の運転規約化【提案】

Phase A（125 エージェント 1 セッションで 711 件抽出）・Phase B（1 セッション = 1 フェーズ文書、批評家ゲート付き）で実証されたループ（`b3/ver3-開発計画-v1.md` §4.1【事実】）を、夜間運転の恒常ループとして規約化する:

```
要件抽出 → 設計 → 実装 → テスト → harvest（蒸留）
   ↑                                    │
   └──── 朝レビューの NG 理由・KPI 参考値 ←┘
```

| 段 | 夜間で回してよい部分 | 人間ゲート |
|---|---|---|
| 要件抽出 | repo 内の裁定録・掲示板ログからの候補抽出ドラフト（V3-AIP-67 の要約バッチと同型） | 要件への昇格は人間 OK |
| 設計 | 既存設計書の矛盾スキャン・改訂ドラフト | 裁定を要する改訂は「要判断」カード |
| 実装 | **夜間では行わない**（第1波実装期間中、夜間運転を実装に使わない — 開発計画 §8 R-01 緩和策） | — |
| テスト | 既存 TC の実行・赤化検知（決定論。モデル呼び出し不要） | — |
| harvest | done プロジェクトからの蒸留ドラフト（B6 接続 — §8） | wiki 正本への merge は人間 OK |
| ループ改善 | NG 理由 jsonl の集計 → タスク定義の改善**提案**（提案止まり。タスク定義の書き換えは人間） | タスク定義変更は人間 |

- NG 理由 → 生成モデル自動更新（Evaluator 共通アーキ V3-AIP-75）は**第2波**。第1波の改善ループは「NG 理由を人間可読に集計し、次のタスク定義に人間が反映する」まで（自動更新を謳わない — 誇張ゼロ）。

### 5.2 KPI 定義表【提案】

計測は全て **`ops\runs\` のラウンド単位 JSON ログ + `decisions.jsonl` からの決定論投影**（N5。モデル不要・再生成可能）。**数字は参考値・価値観>数字**（V3-AIP-85「価値観>世界観>一貫性>正確性>数字」`ver3-最終要件定義書-v1.md:921`）— KPI 悪化を理由に人間ゲートを外す・上限を上げる方向の最適化を**禁止**する（非過激化ゲートの運転版）。

| KPI | 定義 | 計測方法（投影元） | 参考目安（目標値ではない） |
|---|---|---|---|
| 夜間タスク成功率 | success_criteria 達成 run / 全 run | round JSON の最終 round `score` + STOP 理由 | 5 割で十分（失敗は学習データ — V3-AIP-75） |
| 朝レビュー処理時間 | morning-review.md 生成時刻 → decisions.jsonl 最終 append の経過分 | 両ファイルのタイムスタンプ | 10 分/夜以内に収まる分量しか積まない |
| OK 率 | ok / (ok+ng) | decisions.jsonl | 低くても停止しない。連続 0% は §6 で自動停止 |
| 批評家ゲート初回通過率 | 夜間ドラフトが後続の批評家ゲートを一発通過した率 | 批評ログ（Phase C の CI/批評記録）と run_id の突合 | 参考値 |
| トークン/成果物 | 消費 tokens ÷ OK になった成果物数 | round JSON `tokens_used` 累計 ÷ decisions ok 数 | 増加傾向の検知用 |
| コスト/夜 | Σ usd_used | round JSON | 総枠 5 USD 比の消化率 |
| wiki 鮮度 | 最終 ingest からの経過日数（対象 wiki ごと） | ingest ログ（B6 系）の最終日付 | 7 日超で ingest スキャンをタスク候補に |

- 投影スクリプトは `ops\` 配下の決定論スクリプト 1 本（Phase C 実装）。出力は `00-hq\dashboard\` が読む JSON 1 枚（§4 Stage 1 の `side_panel.metrics` 供給元）。

## 6. 安全停止設計

### 6.1 停止条件の一覧【提案】

| # | 条件 | 動作 | 復帰 |
|---|---|---|---|
| S1 | タスクのキャップ到達（tokens/usd/minutes/rounds のいずれか） | STOP マーカー + 当該タスク終了。他タスクは継続 | 自動（翌夜。ただし S5 参照） |
| S2 | 夜間総枠到達 | **全タスク停止**（当夜終了） | 自動（翌夜） |
| S3 | 成果ゼロラウンド（`zero_result_stop`）: ラウンドが成果物 0・差分 0 で終了 | STOP + 「成果ゼロ」理由 | 自動（翌夜） |
| S4 | ラウンド内エラー 2 連続（validate 失敗・ツールエラー等） | STOP + エラー内容をカード化 | 自動（翌夜。ただし S5） |
| S5 | **同一タスクが 2 夜連続で S1/S3/S4 停止** | タスクを `disabled: true` に自動マーク。**人間が再有効化するまで走らない** | **人間のみ** |
| S6 | `night.json` の `enabled: false` / スキーマ validate 不合格 / STOP マーカー既存 | そもそも起動しない | 人間 |
| S7 | ランナー自身の異常終了 | 次回起動時に前回 run の終了記録欠落を検知 → 当該タスクを S5 扱い | 人間 |

### 6.2 エスカレーション【提案】

- エスカレーション先は**常に朝レビュースタック**（夜中に人間を起こさない。通知強度の引き上げ = PushNotification 等は恒常運転裁定時のユーザー選択）。
- S5/S7 のカードは通常成果カードと区別できる形（`state: needs_human`）で最上段に積む。**夜間エージェントが自分でリトライ戦略を発明することを禁止**（escalation はタスク定義の `escalation` キーに書かれた手順 = 原則「止めて報告」のみ）。

### 6.3 ログの append-only 保存【提案】

- `ops\runs\` 配下は**追記のみ**。ラウンド JSON・STOP・decisions.jsonl の UPDATE/DELETE 禁止（条項③。ver3 repo 誕生後は R2 Truth `logs/` 系へのミラー昇格を検討 — B4 §2 keyspace `logs/` 行）。
- run の破棄（表示上の非表示化）は破壊的操作としてキュー③の確認を必須とし、実体ファイルは消さない（月次アーカイブのみ — ワークスペース設計 §1.3 深度制限）。
- 各 run ログの必須フィールド（B4 §10 round_log を具体化）: `{round_n, started_at, ended_at, model, tokens_used, usd_used, artifacts[], score, stop_reason|null}`。

2. **コスト既定値**: タスク 2.00 USD / 夜間総枠 5.00 USD / タスク 2 本/夜 / `enabled: false` 既定 + 有効化に enabled_by 記名必須（§3.1-3.2）。『20ドル』の多層防御 5 層（§3.3）。
3. **朝レビューは Stage 0（Markdown スタック + decisions.jsonl）から開始**。かんばん・ScreenDef 化は後段（§4.2 — 誇張ゼロ）。

5. **試験導入 = wiki 鮮度スキャン + 蓄積データ要約ドラフト 1 本（第1波荷物のみ — B3 §3.2 準拠。台本ドラフトは C-W2 通過後）・1.50 USD 上限（ラウンド境界検査のため 1 ラウンド分の超過余地あり — §3.3 L2/§7.1）・1 夜限り・書込は ops\runs\ のみ**。有効化はユーザーの合図待ち（§7）。
